# PRD: Friensyashki Messenger

## 1) Контекст и цель продукта

Создать мессенджер (аналог Telegram) с постепенным развитием:
- старт: текстовое общение пользователей между собой (MVP);
- далее: поддержка разных форматов данных (медиа, файлы, голос и т.д.), групп/каналов и расширенных возможностей.

Основная цель первого релиза: пользователь может зарегистрироваться/войти (через готовый auth), создать личный диалог и обмениваться текстовыми сообщениями в реальном времени.

## 2.1) Принятые решения (на текущий момент)

- Для MVP делаем backend + минимальный frontend-клиент для ручной проверки сценариев.
- Проверка пользователя в `messenger`: сервис получает токен и валидирует его через gRPC-вызов в `auth`.
- Создание диалога в MVP: по `login`/username (а не по `user_id` напрямую). Реализовано в TASK-004 через gRPC-метод `GetUserByLogin`.
- Версию `messenger` храним в env/config.
- Приоритет после MVP: группы/каналы.

## 3) Текущее состояние (что уже есть)

В проекте уже реализован отдельный `auth`-сервис на Python/FastAPI:
- REST API: `signup`, `login`, `me`, `refresh`, `logout` (`/auth/api/v1/users/...`);
- JWT в `HttpOnly` cookie (`access` + `refresh`);
- Redis blacklist для инвалидированных токенов;
- PostgreSQL для пользователей;
- gRPC метод `GetUserInfoByToken` для валидации access token и получения `user_id`;
- шифрование и хеширование персональных полей (email/phone), хеширование пароля.

Это означает, что для мессенджера аутентификацию нужно **переиспользовать**, а не дублировать.

`messenger`-сервис (v0.1.6):
- FastAPI каркас с health endpoint;
- PostgreSQL + Alembic: 4 таблицы (`dialogs`, `dialog_participants`, `messages`, `message_statuses`);
- Async репозитории (`DialogsRepository`, `MessagesRepository`);
- gRPC-клиент к auth (`GetUserInfoByToken`, `GetUserByLogin`) + FastAPI dependency `get_current_user_id`;
- `POST /dialogs/direct` — создание/получение 1:1 диалога по `target_login` (идемпотентно);
- `GET /dialogs` — список диалогов пользователя с сортировкой по `updated_at` DESC;
- `POST /dialogs/{dialog_id}/messages` — отправка текстового сообщения с идемпотентностью по `client_message_id` и проверкой участия в диалоге;
- `GET /dialogs/{dialog_id}/messages` — история сообщений с пагинацией (limit/offset), доступ только участникам диалога;
- Слои: schemas → service → repository для dialogs и messages;
- Тесты: миграции + CRUD smoke-tests + auth dependency + dialogs endpoint + list dialogs + messages endpoint + message history (testcontainers).

Веб-клиент (TASK-UI-001):
- Минимальный single-page веб-клиент (`web/index.html`) для ручного тестирования;
- Регистрация, вход, выход, список диалогов, создание диалога, отправка/просмотр сообщений;
- Dark theme, responsive layout, XSS-защита через DOM-based escaping;
- Раздача через Nginx gateway на `/web/`;
- Cookie-based аутентификация с `credentials: 'include'` и автоматическим refresh при 403.

## 4) Scope

### 4.1 MVP (обязательный объём)

1. Пользователь авторизуется через существующий `auth`.
2. Пользователь видит список своих диалогов 1:1.
3. Пользователь может создать диалог 1:1 по `user_id`.
3. Пользователь может создать диалог 1:1 по `login`/username.
4. Пользователь отправляет текстовые сообщения.
5. Получатель получает сообщение в реальном времени.
6. Сообщения сохраняются и доступны после перезахода.
7. Есть базовые статусы сообщения:
   - `sent` (принято сервером),
   - `delivered` (доставлено клиенту),
   - `read` (прочитано).

### 4.2 Out of scope для MVP

- Группы и каналы;
- Медиа/файлы/голос;
- Поиск по сообщениям;
- Реакции, ответы, редактирование/удаление;
- E2E-шифрование;
- Push-уведомления.

### 4.3 Post-MVP (следующая волна)

- группы/каналы;
- вложения разных типов;
- пользовательские аватарки (загрузка, обновление, хранение в объектном хранилище);
- синхронизация нескольких устройств;
- офлайн-доставка и push;
- расширенная модерация и антиспам.

## 5) Функциональные требования MVP

### FR-1. Идентификация пользователя
- Все запросы в messenger-сервис должны быть связаны с валидным пользователем.
- Проверка access token через интеграцию с `auth` (gRPC или внутренний gateway-слой).

### FR-2. Диалоги 1:1
- Создание диалога между двумя пользователями.
- Идемпотентность: повторное создание между теми же пользователями не создаёт дубликат.
- Получение списка диалогов пользователя с сортировкой по времени последнего сообщения.

### FR-3. Сообщения
- Отправка текстового сообщения в диалог.
- Получение истории сообщений (пагинация).
- Валидация принадлежности пользователя к диалогу.

### FR-4. Realtime
- Доставка новых сообщений через WebSocket.
- Подтверждения доставки/прочтения.
- Повторное подключение клиента без потери консистентности состояния.

### FR-5. Базовая надежность
- Сообщение после ACK сервера не теряется.
- Идемпотентность отправки по `client_message_id`.

## 6) Нефункциональные требования MVP

- **Производительность:** P95 отправки текстового сообщения < 300 мс при целевой нагрузке MVP.
- **Доступность:** не ниже 99.5% для API мессенджера.
- **Безопасность:** доверяем только токенам, подтверждённым через `auth`; обязательная авторизация всех приватных методов.
- **Наблюдаемость:** структурированные логи, метрики ошибок/латентности, health-check.

## 7) Технологии

### 7.1 Подтверждённые
- Python
- PostgreSQL
- Redis
- Kafka
- **FastAPI** для REST + WebSocket.
- **SQLAlchemy + Alembic**.
- **Nginx** как reverse proxy.
- **pytest + pytest-asyncio + httpx** для автотестов.
- **Pydantic v2** для схем/валидации.
- **Celery/RQ + Redis** для фоновых задач.
- **Prometheus + Grafana** для метрик.

### 7.2 Стратегия объектного хранилища

- `Prod`: использовать внешний managed S3 (арендованный провайдер).
- `Local/dev`: использовать S3-совместимый аналог в Docker (`MinIO`).
- Приложение должно работать через единый S3-compatible интерфейс; переключение `prod/local` делается только конфигом (`endpoint`, `keys`, `bucket`, `ssl`, `region`).

## 8) Архитектура (черновая)

- `auth` — отдельный сервис идентификации/сессий.
- `messenger` — сервис чатов и сообщений:
  - REST API (диалоги, история, статусы);
  - WebSocket gateway (realtime события);
  - PostgreSQL (история, диалоги, членство);
  - Redis (presence, ephemeral-state, возможно pub/sub в MVP).

### 8.1 Границы изменений сервисов

- `auth`-сервис можно изменять по усмотрению в рамках задач мессенджера, если это улучшает интеграцию, безопасность, стабильность или DX.
- При изменениях `auth` сохраняется обратная совместимость публичных контрактов или заранее фиксируется план миграции контрактов в PRD/задачах.

## 9) Модель данных MVP (минимум)

### Таблица `dialogs`
- `id` (UUID, PK)
- `type` (`direct`)
- `created_at`, `updated_at`

### Таблица `dialog_participants`
- `dialog_id` (FK -> dialogs)
- `user_id` (UUID из auth)
- `joined_at`
- уникальный индекс (`dialog_id`, `user_id`)

### Таблица `messages`
- `id` (UUID, PK)
- `dialog_id` (FK -> dialogs)
- `sender_id` (UUID)
- `client_message_id` (string, для идемпотентности)
- `text` (TEXT)
- `created_at`
- уникальный индекс (`dialog_id`, `sender_id`, `client_message_id`)

### Таблица `message_statuses`
- `message_id` (FK -> messages)
- `user_id` (UUID)
- `status` (`delivered` | `read`)
- `updated_at`
- уникальный индекс (`message_id`, `user_id`)

## 10) API (MVP, draft)

- `POST /messenger/api/v1/dialogs/direct` — создать/получить диалог 1:1
  - входные данные MVP: `target_login`
- `GET /messenger/api/v1/dialogs` — список диалогов
- `GET /messenger/api/v1/dialogs/{dialog_id}/messages?limit=&offset=` — история
- `POST /messenger/api/v1/dialogs/{dialog_id}/messages` — отправить сообщение
- `POST /messenger/api/v1/messages/{message_id}/read` — отметить прочитанным
- `WS /messenger/api/v1/ws` — realtime канал

## 12) Критерии готовности MVP

- Все задачи `TASK-001 ... TASK-011` завершены;
- Автотесты проходят стабильно;
- E2E сценарий "два пользователя общаются в 1:1" проходит без ручных фиксов;
- Документация по запуску и проверке MVP актуальна.

## 13) Риски и ограничения

- Зависимость от `auth` как внешнего сервиса (availability/latency);
- WebSocket масштабирование потребует отдельной стратегии (sticky sessions или broker);
- Без брокера в MVP масштабирование realtime ограничено.

## 13.1) Принятые решения

- Решение принято:
  - для MVP используем только `WebSocket`;
  - `long-polling fallback` добавляем отдельной задачей после стабилизации `v0.2.x`.

## 15) Code Style и качество кода

Ниже зафиксированы правила разработки для `messenger`, синхронизированные с текущими настройками проекта и дополнительными договорённостями.

### 15.1 Базовые инструменты и конфиги

- `ruff` (`ruff.toml`):
  - `line-length = 100`, `indent-width = 4`;
  - правила линтинга: `E`, `W`, `F`, `I`, `N`, `UP`, `B`, `C4`, `BLE`, `A`, `T20`;
  - игнорируются: `B008`, `N818`;
  - порядок импортов через `isort` c `known-local-folder = ["src", "tests"]`.
- `mypy` (`setup.cfg`):
  - `python_version = 3.12`;
  - `disallow_untyped_defs = True`, `check_untyped_defs = True`;
  - включены проверки на лишние касты и неиспользуемые ignore (`warn_redundant_casts`, `warn_unused_ignores`).
- `pre-commit` (`.pre-commit-config.yaml`):
  - обязательные хуки качества (yaml/eof/whitespace/merge-conflict/private-key/no-commit-to-main);
  - обязательные `ruff` и `ruff-format`.

### 15.2 Нейминг (дополнительные соглашения)

- Функции/методы должны иметь **говорящие имена**.
- Всё, что получает/извлекает данные, нужно именовать с префиксом `get_`.
- Всё, что возвращает `bool`, нужно именовать с префиксом `is_`.

### 15.3 Размер и читаемость методов

- Необязательное, но **очень-очень желательное** правило: держать методы до 10 строк.
- Если метод неизбежно больше, его следует декомпозировать на подметоды с понятной ответственностью.

### 15.4 Документирование кода

- Не использовать inline-комментарии через `#` в теле бизнес-логики.
- Использовать docstring в начале функции/метода/класса для пояснения назначения и поведения.
- Исключения для `#`-комментариев допустимы только в технических случаях (например, `noqa`, `type: ignore`, автогенерируемые файлы).
