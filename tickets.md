# Tickets: Friensyashki Messenger

## Правило версионирования

- новая функциональность задачи -> bump patch (`v0.1.0` -> `v0.1.1`);
- если задача существенно расширяет API/контракты, допускаем bump minor.

## Этап 0: проектный каркас

1. **TASK-001 | Версия `v0.1.0`** ✅
   - Что делаем: создать каркас `messenger`-сервиса (структура, конфиг, health endpoint, docker-compose integration).
   - Тесты:
     - `GET /health` -> `200`;
     - сервис поднимается в docker без ошибок.

2. **TASK-002 | Версия `v0.1.1`** ✅
   - Что делаем: подключить PostgreSQL + Alembic, создать базовые миграции (`dialogs`, `dialog_participants`, `messages`, `message_statuses`).
   - Тесты:
     - миграции применяются на чистой БД;
     - повторный прогон миграций не ломается;
     - базовые CRUD smoke-tests репозиториев.

## Этап 1: интеграция с auth

3. **TASK-003 | Версия `v0.1.2`** ✅
   - Что делаем: middleware/dependency для идентификации пользователя через `auth` (через gRPC `GetUserInfoByToken`).
   - Тесты:
     - валидный токен -> доступ к защищенному endpoint;
     - невалидный/просроченный/blacklist токен -> `403`.

## Этап 2: диалоги 1:1

4. **TASK-004 | Версия `v0.1.3`** ✅
   - Что делаем: `POST /dialogs/direct` (создание/получение 1:1 диалога по `target_login`).
   - Тесты:
     - первый вызов создаёт диалог;
     - повторный вызов с той же парой возвращает существующий;
     - пользователь не может создать диалог с самим собой;
     - несуществующий `target_login` возвращает корректную ошибку.

5. **TASK-005 | Версия `v0.1.4`** ✅
   - Что делаем: `GET /dialogs` со списком диалогов пользователя.
   - Тесты:
     - пользователь видит только свои диалоги;
     - сортировка по последней активности корректна.

## Этап 3: текстовые сообщения

6. **TASK-006 | Версия `v0.1.5`**
   - Что делаем: `POST /dialogs/{id}/messages` (сохранение текста + идемпотентность по `client_message_id`).
   - Тесты:
     - сообщение сохраняется и возвращается с `id`, `created_at`;
     - повтор с тем же `client_message_id` не создаёт дубликат;
     - отправка в чужой диалог запрещена.

7. **TASK-007 | Версия `v0.1.6`**
   - Что делаем: `GET /dialogs/{id}/messages` (история с пагинацией).
   - Тесты:
     - корректные `limit/offset`;
     - порядок сообщений детерминированный;
     - доступ только участникам диалога.

## Этап 3.5: минимальный UI для ручного тестирования

8. **TASK-UI-001 | После `v0.1.6`**
   - Что делаем: минимальный веб-клиент (HTML/JS) для ручной проверки сценариев: логин через `auth`, список диалогов, создание диалога, отправка и просмотр сообщений. Позднее дополняется WebSocket-событиями из Этапа 4.
   - Тесты:
     - клиент позволяет авторизоваться и увидеть список диалогов;
     - пользователь может создать диалог и отправить сообщение;
     - история сообщений отображается корректно.

## Этап 4: realtime и статусы

9. **TASK-008 | Версия `v0.1.7`**
   - Что делаем: WebSocket подключение пользователя, получение новых сообщений online.
   - Тесты:
     - два клиента в диалоге получают событие `new_message`;
     - после reconnect клиент продолжает получать события.

10. **TASK-009 | Версия `v0.1.8`**
   - Что делаем: статус `delivered` при доставке в активную сессию.
   - Тесты:
     - при активном WS у получателя статус обновляется на `delivered`;
     - статусы не проставляются неучастникам диалога.

11. **TASK-010 | Версия `v0.1.9`**
    - Что делаем: `POST /messages/{id}/read` и статус `read`.
    - Тесты:
      - участник может отметить сообщение прочитанным;
      - повторный вызов идемпотентен;
      - отправитель видит обновление статуса.

## Этап 5: стабилизация MVP

12. **TASK-011 | Версия `v0.2.0`**
    - Что делаем: observability (логи/метрики), лимиты, базовые перф-тесты, документация.
    - Тесты:
      - smoke e2e: login -> create dialog -> send -> receive -> read;
      - регрессионный прогон API + WS;
      - нагрузочный тест на целевую MVP-нагрузку.

## Backlog после стабилизации v0.2.x

- **TASK-012 | Версия `v0.2.1` (план)**
  - Что делаем: добавить `long-polling fallback` для realtime при недоступности WebSocket.
  - Тесты:
    - при штатном состоянии используется WebSocket;
    - при недоступном WebSocket клиент переключается на long-polling;
    - доставка сообщений сохраняется без потери событий.

- **TASK-SEC-001 | Версия `v0.2.2` (план)**
  - Что делаем: настроить SSL для PostgreSQL и добавить `sslmode=require` в DSN обоих сервисов (`auth`, `messenger`). В production — сертификаты для PG; в docker-dev — опционально.
  - Тесты:
    - подключение к PostgreSQL с `sslmode=require` проходит без ошибок;
    - подключение без SSL отклоняется сервером (production).

- **TASK-013 | Версия `v0.2.3` (план)**
  - Что делаем: добавить пользовательские аватарки (upload/update/get) с хранением в S3-совместимом хранилище (`prod` — managed S3, `local` — MinIO).
  - Тесты:
    - пользователь может загрузить аватар допустимого формата и размера;
    - обновление аватарки заменяет ссылку на предыдущую;
    - получение профиля возвращает актуальный URL/ключ аватарки;
    - при невалидном формате или превышении лимита возвращается корректная ошибка.
