# Tickets: Friensyashki Messenger

## Правило версионирования

- новая функциональность задачи -> bump patch (`v0.1.0` -> `v0.1.1`);
- если задача существенно расширяет API/контракты, допускаем bump minor.

   - Тесты:
     - `GET /health` -> `200`;
     - сервис поднимается в docker без ошибок.

2. **TASK-002 | Версия `v0.1.1`** ✅

     - повторный прогон миграций не ломается;

    - Тесты:

10.2 **TASK-009b** Сделать, чтобы пользователь мог отправить сообщение только раз в секунду, чтобы не было спама. При этом сообщение не должно стираться у него из поля ввода. Переменную с 1 секундой нужно вынести в конфиг, чтобы этот функционал можно было поменять в настройках в любой момент, например поставить 0.5 секунд

11. **TASK-010 | Версия `v0.1.9`**
    - Что делаем: `POST /messages/{id}/read` и статус `read`.
    - Тесты:
      - участник может отметить сообщение прочитанным;
      - повторный вызов идемпотентен;
      - отправитель видит обновление статуса.

12. **TASK-011 | Ошибки при регистрации дублируются**
    - Что делаем: исправить дублирование сообщений об ошибках в форме регистрации.
    - Поведение: при неверном email ошибка показывается один раз; при несоответствии пароля требованиям одна и та же ошибка показывается дважды.
    - Примеры со скриншотов:
      - Email: при вводе «vjk» — одна ошибка: «value is not a valid email address: An email address must have an @-sign.»
      - Пароль: при коротком пароле — дублирование: «Password must be at least 8 characters • Password must be at least 8 characters»
    - Тесты:
      - каждое сообщение об ошибке валидации отображается один раз;
      - для email и для пароля нет дублирования текста ошибки.

## Backlog после стабилизации v0.2.x

- **TASK-015 | Версия `v0.2.1` (план)**
  - Что делаем: добавить `long-polling fallback` для realtime при недоступности WebSocket.
  - Тесты:
    - при штатном состоянии используется WebSocket;
    - при недоступном WebSocket клиент переключается на long-polling;
    - доставка сообщений сохраняется без потери событий.

- **TASK-SEC-001 | Версия `v0.2.2` (план)**
  - Что делаем: настроить SSL для PostgreSQL и добавить `sslmode=require` в DSN обоих сервисов (`auth`, `messenger`). В production — сертификаты для PG; в docker-dev — опционально.
  - Тесты:
    - подключение к PostgreSQL с `sslmode=require` проходит без ошибок;
    - подключение без SSL отклоняется сервером (production).

- **TASK-016 | Версия `v0.2.3` (план)**
  - Что делаем: добавить пользовательские аватарки (upload/update/get) с хранением в S3-совместимом хранилище (`prod` — managed S3, `local` — MinIO).
  - Тесты:
    - пользователь может загрузить аватар допустимого формата и размера;
    - обновление аватарки заменяет ссылку на предыдущую;
    - получение профиля возвращает актуальный URL/ключ аватарки;
    - при невалидном формате или превышении лимита возвращается корректная ошибка.

- **TASK-017 | Версия `v0.2.4` (план)**
  - Что делаем: возможность смены логина пользователем. После смены логина сервер auth выдаёт новый JWT с новым логином; клиент обязан обновить токен (refresh), чтобы в UI сразу отображался новый логин без лага, когда подсасывается старый логин из старого токена.
  - Тесты:
    - успешная смена логина возвращает новый access (и при необходимости refresh) токен с новым `login` в payload;
    - клиент после смены логина использует новый токен; в UI отображается новый логин без промежуточного отображения старого;
    - валидация логина (уникальность, формат); корректные ошибки при конфликте или невалидном значении.

- **TASK-UI-002 | После `v0.2.4` (план)**
  - Что делаем: UI для смены логина (форма/модалка в настройках профиля): поле нового логина, подтверждение, вызов API смены логина, обновление токена и отображения логина в приложении без перезагрузки.
  - Тесты:
    - пользователь может открыть форму смены логина и отправить запрос;
    - после успешной смены логин в шапке/профиле обновляется без перезагрузки страницы;
    - при ошибке (занятый логин, невалидный формат) отображается сообщение об ошибке.
